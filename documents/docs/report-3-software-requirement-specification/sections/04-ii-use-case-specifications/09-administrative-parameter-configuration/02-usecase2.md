### 5.1 Administrative Parameter Configuration

#### 5.1.2 Manage Third-Party API Credentials

<table>
<tr><td>Primary Actors</td><td>Admin</td><td>Secondary Actors</td><td>Payment Gateway, External Registration System, AI API, Google Maps API, Mail Gateway, Cloud Storage Service</td></tr>
<tr><td>Description</td><td colspan="3">Allows the Admin to maintain approved credentials, endpoints, and activation status for the system's third-party integrations, including VNPay, Klook, Gemini, Google Maps/Places, Mland SMTP, and cloud storage.</td></tr>
<tr><td>Preconditions</td><td colspan="3">1. The Admin is authenticated and authorized to manage integration credentials.<br>2. The target integration type is supported by the platform.<br>3. The Admin has received valid credentials and endpoint information through an approved operational channel.</td></tr>
<tr><td>Postconditions</td><td colspan="3">• Valid credentials and endpoints are stored securely and associated with the selected integration.<br>• Secrets are masked in the user interface and are not exposed in logs.<br>• The integration is enabled only after validation or an explicit approved activation decision.<br>• Previous credentials remain recoverable through audit/rotation history according to retention policy.</td></tr>
<tr><td>Normal<br>Sequence/Flow</td><td colspan="3"><em>Manage Third-Party API Credentials</em><br>1. The Admin opens third-party integration configuration.<br>2. The system displays supported integrations and masked current configuration.<br>3. The Admin selects an integration and enters or updates its endpoint, credentials, and active state.<br>4. The system validates the required fields and integration-specific format.<br>5. The system performs a safe connection or credential test when supported, without creating a business transaction.<br>6. The Admin confirms the change.<br>7. The system encrypts/stores the credentials, records the change, and displays the updated masked status.</td></tr>
<tr><td>Alternative<br>Sequences/Flows</td><td colspan="3"><em>Step 3 — Unsupported integration or missing required field</em><br>The system rejects the configuration and identifies the missing/unsupported data.<br><br><em>Step 5 — Credential or endpoint test fails</em><br>The system reports the failure and does not activate the new configuration.<br><br><em>Step 6 — Admin cancels</em><br>No credential change is saved.<br><br><em>Step 7 — Secure storage fails</em><br>The system does not activate the credential and displays an operational error.<br><br><em>Credential rotation</em><br>The system replaces the active secret only after the new configuration is valid and retains an audit record of the rotation.</td></tr>
<tr><td>Business Rule</td><td colspan="3">BR-55-01, BR-55-02, BR-55-03</td></tr>
</table>

<table><tr style="background-color:#f4cccc"><th>ID</th><th>Rule Definition</th></tr><tr><td>BR-55-01</td><td>Only an authorized Admin may create, update, activate, deactivate, or rotate third-party integration credentials.</td></tr><tr><td>BR-55-02</td><td>Credentials must be stored securely, masked from ordinary display, and excluded from application logs and error messages.</td></tr><tr><td>BR-55-03</td><td>An integration must not be activated when its required credentials or endpoint validation fails.</td></tr></table>
