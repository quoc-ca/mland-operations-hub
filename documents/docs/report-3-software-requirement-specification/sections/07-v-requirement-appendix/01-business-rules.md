<!-- # Architecture Convention

## Purpose

PPSWBS V1 is a Spring Modulith modular monolith. The convention keeps business ownership explicit while retaining one Spring Boot deployment and synchronous in-process calls where appropriate. It is an implementation convention, not a decision on production deployment, payment provider, retention, logging implementation, or other unresolved NFR controls.

## Module structure

Each business module owns this internal structure when its first approved feature is implemented:

```text
<module>/
  facade/          # explicit Java API exposed to other business modules
  web/             # REST/page controllers and HTTP DTOs
  application/     # use cases and transaction boundaries
  domain/          # JPA entities, value objects, business invariants
  infrastructure/  # Spring Data repositories, queries, external adapters
```

Only `facade/` is a Spring Modulith named interface. A module must not import another module's controllers, HTTP DTOs, entities, repositories, or infrastructure adapters. The technical `configuration` and `common` packages are not business modules. `common` may contain only typed errors, correlation IDs, clock/ID abstractions, and security context; it must not become a shared business-model package.

## V1 ownership map

| Module | Owns |
| --- | --- |
| `members` | External identity mapping, Member status/entitlement, consent, policy acceptance, Member audit and future profile. |
| `workshopbooking` | Capacity, booking, booking contact-email confirmation and expiry. |
| `catalogue` | Workshop packages, ready-ring product definitions, components and prices. |
| `designreview` | Design input, consented references, feasibility review and override. |
| `billing` | Invoices, adjustments, customer consent and settlement facts. |
| `payments` | Payment attempts, transactions and verified gateway callbacks. |
| `readyringsales` | Ready-ring availability, Member sales, reservation and delivery choice. |
| `fulfilment` | Continuation, custody, release and handoff evidence. |
| `operations` | Staff check-in and operational workflows. |
| `technicaladmin` | Technical configuration/monitoring, without business-record mutation. |

Audit evidence remains in the domain whose workflow produced it. V1 has no central audit event store or aggregate Admin Technical audit screen.

## Dependency and event rules

Facade calls are synchronous and one-way by default. A domain event is used only for a callback, an inherently asynchronous workflow, or removal of a module cycle. Internal events remain inside the Spring Boot application in V1; Kafka and microservices are not implied. Events carry minimal identifiers/version data, are published after the producing transaction commits, and consumers must be idempotent.

For example, billing publishes a payment request and payments publishes a verified payment confirmation. This prevents a `billing` to `payments` and `payments` to `billing` dependency cycle while keeping the gateway webhook boundary correct. Ready-ring sales similarly publishes a fulfilment-start event rather than creating a sales-to-fulfilment-to-sales call cycle.

## Enforcement

Every business module is a closed `@ApplicationModule` with declared allowed dependencies and a `facade/` `@NamedInterface`. `ApplicationModules.verify()` runs in automated tests and rejects dependency cycles, undeclared dependencies, and access to module internals. Runtime fail-fast module verification is not enabled in V1. -->

## 1. Business Rules

|GBR-ID|Rule Statement|Applies To|Rationale|Enforced By|
|---|---|---|---|---|
| GBR-01 | A workshop booking requires a selected package before its schedule/slot and design path are chosen. | UC-21 | The package price determines the deposit. | Workshop booking flow |
| GBR-02 | A workshop booking group is confirmed only after verified VNPay payment of its collection (each ticket up to 200,000 VND), or without VNPay when nothing has to be collected. | UC-21, UC-22 | Reserves capacity against committed payment. | Workshop booking flow |
| GBR-03 | A VNPay Return URL never confirms payment. The application accepts only a valid signed IPN or the defined signed QueryDR recovery result while the hold remains active. | UC-22, UC-55, UC-69 | Prevents client-side or duplicate payment confirmation. | VNPay adapter and payment workflow |
| GBR-04 | A workshop booking group is held for 12 minutes and its VNPay link expires 2 minutes before the hold ends; a retail VNPay checkout is held for 10 minutes (GBR-37). A custom order has no capacity hold: its payment link lasts until the quote deadline. An unpaid hold is released when no valid confirmation exists. | UC-21, UC-22, UC-54, UC-55, UC-69 | Limits blocked inventory and capacity. | Hold-expiry workflow |
| GBR-05 | A custom design request is submitted only by a signed-in Member after ownership, consent, input and security checks, and is reviewed by Staff or a Manager with a written explanation. No AI assesses it, and the request has no workshop-booking side effect. Revision follows the approved Feature-004 policy. | UC-39, UC-40, UC-41 | Separates human design review from workshop booking and custom manufacturing. | Custom design request workflow |
| GBR-07 | A custom-manufacturing order is Member-only and is created from a reference image or supported manual configuration, optional requested deadline, and fulfilment method. It requires human review and a Manager-approved quote before payment; it is not added to a retail cart and is not governed by a configurable queue in V1. | UC-67, UC-69 | Custom manufacturing has a distinct lifecycle without queue configuration. | Custom-order workflow |
| GBR-08 | A custom order is paid in one complete payment equal to the active quote. There is no deposit, deferred balance, or later final-balance payment. If verified full payment is not received before the quote deadline, the quote/order expires or is cancelled; no custom queue hold is created or released. | UC-69, UC-71 | Prevents partial-payment ambiguity and keeps the custom order independently payable. | Custom-order and VNPay workflows |
| GBR-09 | A paid retail order uses store pickup or GHTK. Staff prepares it and marks it ready; for pickup Staff records the handover, and for GHTK the partner account records the courier pickup and delivery. There is no GHTK provider tracking. | UC-57 to UC-61, UC-73 | Matches the recorded custody steps. | Fulfilment workflow |
| GBR-10 | Each retail order and each workshop booking uses the best applicable automatic discount, if any, plus at most one voucher chosen by the customer. Loyalty points may be combined with an automatic discount, and with a voucher only if that voucher allows points; points are a non-cash discount and limits are Manager-configured. | UC-44, UC-48, UC-51 | Defines the minimum V1 loyalty/promotion policy. | Checkout and operational-parameter configuration |
| GBR-11 | Retired: no partner booking channel exists. Mland is the sole authority for sellable sessions, capacity and tickets. | — | Partner channels were removed from V1 (Stakeholder statement, Feature-003 owner, 2026-11-25). | None for the retired integration |
| GBR-13 | The application retains Basic AI (Gemini) text prompts/responses for at most 30 days. Feature-004 reference images, custom reference images, delivery data, and payment/audit records follow their approved retention periods. | UC-33, UC-39, UC-67 and NFR | Limits personal-data retention to the approved purpose. | Data-retention controls |
| GBR-14 | Product review, price and publication are separate states. A Manager approves, adjusts or rejects products and prices; an approved price is applied as a separate action, and the first publication requires an approved review, an active category, a usable image and an applied price for every size, while a product that has been published before can be published again when at least one size has an applied price. Only a Manager publishes, hides or shows a whole product again. A Manager's create screen, Publish now and Change price send these steps as separate audited commands and never approve a Pending review or price submitted by Staff in one click. | UC-12 to UC-17 | Keeps catalogue prices accountable and prevents unreviewed content from being sold. | Product review, pricing and publication workflow |
| GBR-15 | Sizes come only from the fixed size table 5 to 29; no other size exists. A product is created with 1–25 sizes from that table, each with one read-only SKU `SP{product code}-S{size}` that never changes and is never reused. Saved sizes cannot be changed or removed; a size from 5 to 29 that the product does not have yet may be added later at one selling branch, and other branches do not sell it until they add their own quantity. Quantity is kept per size at each selling branch and cannot fall below valid holds at that branch; the price is shared by all branches. | UC-11 to UC-13 | Gives each sellable ring variant a stable identity and protects held stock. | Product creation, import and quantity update |
| GBR-16 | Hiding, stopping sale of a size or at a branch, changing price, deactivating a category or deleting a product never cancels valid holds, changes accepted orders or removes history; deletion is a soft delete. | UC-12, UC-16, UC-17, UC-18 | Protects terms already agreed with customers. | Product management and checkout revalidation |
| GBR-17 | Excel import creates draft products under the same rules as manual creation, validates the whole file before creating anything, and is all or nothing. Quantities are entered per selected branch within the actor's scope, and a preview expires after 60 minutes. | UC-13 | Allows bulk entry without weakening data quality. | Product import workflow |
| GBR-18 | Only a Manager manages vouchers, automatic discounts and the loyalty point policy. Admin has no promotion or point permission. Promotion Management pages are shown only to the Manager role. | UC-45, UC-46, UC-51 | Keeps commercial decisions with the business owner. | Role-based access checks |
| GBR-19 | The automatic discount is calculated first and split over the lines or tickets in its scope; the voucher is then calculated on the amount of its in-scope lines or tickets after that automatic discount, and points come last. The retail eligible amount includes only purchasable lines in scope (for a branch-limited voucher, only lines at branches in scope) and excludes shipping; a workshop discount applies only to the tickets in scope. A voucher that gives no further discount after the automatic discount is rejected. | UC-48 | Prevents stacked discounts and defines a clear discount base. | Checkout and booking calculation |
| GBR-20 | For a workshop booking, the automatic discount, then the voucher and then points are subtracted from the package fee; Workshop Management calculates the deposit and the remaining amount from the fee after discounts. A fee after discounts of 0 VND is accepted; only a negative fee is rejected. | UC-44, UC-48 | Avoids discounting or deducting points twice across deposit and remaining payments. | Workshop booking and deposit workflow |
| GBR-21 | Points and voucher uses are held when an order or booking is accepted and finalized exactly once after verified payment or acceptance of a valid 0 VND transaction; they are released on expiry or cancellation before payment and refunded once after a confirmed valid or Mland workshop cancellation, per branch order or per ticket where the transaction is split. A finalized voucher use is refunded only if the voucher has not expired when the cancellation is decided; the points used are always refunded. | UC-44, UC-48, UC-50 | Ensures customers do not lose benefits and limits are not exceeded. | Benefit hold, release and refund workflow |
| GBR-22 | Points are earned once per transaction on the amount actually paid after discounts and points, excluding shipping, rounded down: after verified full retail payment, or when a workshop is completed and fully paid; a multi-ticket booking earns per completed ticket from one group total. Guest bookings earn no points. | UC-49 | Rewards real spending in both services from one shared balance. | Point earning workflow |
| GBR-23 | Policy and program changes apply only to transactions accepted afterwards; accepted orders and bookings keep the discount, points and policy recorded at acceptance. | UC-45, UC-46, UC-51 | Honors terms already agreed with customers. | Policy snapshot at acceptance |
| GBR-24 | A product is sold at one or more active branches from the shared branch list; quantity and sale status are kept per size at each branch, and a customer can buy only at a branch that is active and where the size is on sale and available. A Manager manages stock at every active branch and may only change the quantity at an inactive branch; a Staff manages stock only at assigned active branches, and changes content, images and proposed prices only of products sold at one of them. | UC-10 to UC-14 | Each branch holds different stock, while one product definition and price are shared. | Branch stock, branch scope checks and public availability |
| GBR-25 | A product voucher may be limited to one or more branches; only cart lines whose branch is in scope are eligible, and the branch scope cannot change after creation. Automatic discounts have no branch limit. | UC-45 to UC-48 | Lets a promotion target the stock of a specific branch. | Program validation and checkout calculation |
| GBR-26 | Product pages show the price after the largest automatic discount and then the best voucher for one unit, labelled "Price after voucher {code}" (with "· at {branch}" for a branch-limited voucher), and the available quantity per size; on Product Details the price is recalculated for the chosen branch. The vouchers considered are active public vouchers and, for a signed-in Member, usable vouchers in My Saved Vouchers; points are never subtracted. This display never replaces the checkout quote or cart check, and a failure to read promotions never blocks the page. | UC-10, UC-11, UC-47 | Shows customers the current offer without promising a final amount. | Public product card and product details |
| GBR-27 | A rejected write request to promotion or loyalty management is recorded with the actor, the request path containing only identifiers, the error code and the rejected field names, without values, tokens or personal data. | UC-45, UC-46, UC-47, UC-51 | Keeps evidence of refused changes without storing sensitive data. | Promotion and loyalty audit |
| GBR-28 | A workshop automatic discount is limited to one or more packages, with no branch, date or session limit and no use limits, always combines with points and applies to every direct website booking, including a Guest's; a Guest's discount is recorded without a Member, points or voucher. | UC-45, UC-48, UC-49, UC-50 | Lets the public package price show a discount every customer actually receives. | Program validation and workshop booking calculation |
| GBR-29 | Workshop package pages show the price after the largest workshop automatic discount and then the best workshop voucher for one ticket, labelled "Price after voucher {code}" (with "· at {branch}" for a branch-limited voucher; date- or session-limited vouchers are not counted); viewers see the best public voucher and a signed-in Member also a better saved voucher. Points are never subtracted, the workshop cart uses the server quote, and a failure to read promotions never blocks the page. | UC-47 | Shows the best available price without promising a final amount. | Public workshop package card and details |
| GBR-30 | A maximum discount is entered only for a percentage discount; for a fixed amount the cap is stored equal to the amount. | UC-45, UC-46 | Avoids a cap field that has no effect. | Program validation |
| GBR-31 | Buy Now on a product page sends the same add-to-cart request as Add to Cart and then opens the checkout with only that cart line; Product Management never creates an order or calculates the amount to pay. | UC-10, UC-11, UC-52, UC-54 | Keeps cart and checkout ownership with Order Management. | Product details buy panel |
| GBR-32 | Each submission of a product review or price proposal records the submitter's branch scope at that time, and this snapshot is never rewritten; the submitter, branches and decider are shown in management for information only and never change permissions or appear in public reads. | UC-12, UC-14, UC-15 | Keeps an accurate history of who proposed and decided. | Product review and price proposal records |
| GBR-33 | After a product's first publication, a size without an applied price, such as a newly added size waiting for price approval, does not remove the product from publication but is not shown publicly, not counted in public prices or filters and cannot be added to the cart; it appears once its approved price is applied. | UC-10 to UC-17 | Lets a published product keep selling its other sizes while a new size waits for its price. | Public catalogue reads and availability checks |

For each ticked line it shows the line's own share of the previewed automatic discount and voucher, never a share of a discount that does not cover the line; points are deducted from the total only, and checkout recalculates and freezes every amount. | UC-53, UC-54 | Shows each line the price its branch order really gets without promising the final amount. | Cart promotion preview |

| GBR-42 | The executive dashboard is Manager-only. It counts only verified records for the chosen day, week, month or year in Vietnam time and for all branches or one, compares each figure with the previous period of the same length, and marks missing or unreadable data instead of showing it as zero or complete. | UC-64 | Keeps executive figures trustworthy and restricted. | Executive reporting service |
| GBR-43 | Best sellers rank the top 5 products by units in VND branch orders paid in the period, and the top 5 workshop packages by tickets confirmed, completed or marked no-show in booking groups placed in the period at the branch of the first session; ties go to the higher amount before discounts. | UC-64 | Shows what sells using the same facts as the revenue figures. | Executive top-seller service |
