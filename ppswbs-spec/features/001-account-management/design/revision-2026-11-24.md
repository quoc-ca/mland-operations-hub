**Date updated**: 2026-11-27

**Last updated by**: Phan Sơn

This revision records the product decisions made and clarified on 2026-11-24 and the 2026-11-25 demo-preview scope. It supersedes conflicting US3 invitation and US5 role-catalogue descriptions in older FE-001 artifacts. Both feature approval records authorize scoped implementation; live MEMBER retirement remains deferred to T117 and requires separate approval. Application behavior and delivery have not been verified for this revision.

## Decisions and acceptance

1. An ADMIN creates STAFF or MANAGER with required normalized email and name, optional valid phone, and distinct currently active Workshop Location IDs (exactly one for STAFF, at least one for MANAGER). No password or invitation opt-out appears in this form. CARRIER retains its separate direct-provisioning flow.
2. The server checks both MySQL Account ownership and Firebase identity occupancy before provisioning. A collision with an existing STAFF or MANAGER routes the ADMIN to maintenance; ADMIN and CARRIER collisions cannot be replaced here. A MEMBER collision opens an authenticated ADMIN-only review showing name, phone, email, status, addresses, the server-stored retail cart, retail purchase history, and workshop booking history. The unconfirmed workshop cart is browser-only and is outside the review/export. A Firebase-only collision states that Mland has no Account data to export. No other account's data is shown before ADMIN authorization and a positive collision resolution.
3. The MEMBER review offers an on-demand JSON download containing those fields and records, with source IDs, timestamps and a generated-at timestamp. PDF/TXT are excluded. The download is optional, generated from current source data, never persisted as a new server artifact, never contains credentials, raw tokens, payment secrets or another person's data, and is audited. The UI makes no special note about the omitted browser-only cart. Before replacement, the ADMIN sees a fresh review and confirms the exact target Account/email. If source data changes between review and confirm, return conflict and require a new review. Export does not itself authorize replacement.
4. Replacement is blocked whenever an accepted retail order or workshop booking has a nonterminal obligation according to its owning feature. A populated retail cart without an accepted order is not a blocker. The ADMIN sees the blocking reference and neutral reason, cannot complete payment, cancel or otherwise act for the MEMBER in this flow; requesting the person to finish the transaction is outside the system. If both owners confirm no open obligation, replacement suspends/revokes the old MEMBER session, removes its Firebase identity and active login-email ownership, and de-identifies the old Account while preserving its opaque Account ID and mandatory commerce, booking and audit references. It does not delete historical transactions or retained audit. The old Account cannot sign in again. Provider/DB partial failure is explicitly reconciled before creating the new identity; a failed retirement never creates STAFF/MANAGER. A Firebase-only collision may be deleted after separate confirmation. Every review/export/retirement command records safe audit evidence. This workflow needs a new Account-retirement model and cross-feature read contracts; deletion by cascade is forbidden.
5. Provision one real Firebase UID and bind it to exactly one PENDING_SETUP Account before issuing an invitation. Persist normalized request digest and provisioning progress; same idempotency key plus unchanged request returns the same result, any changed field returns 409. The binding never uses email equality as proof of identity. A provider-created identity with failed DB commit is reconciled or removed before retry; no orphan is treated as an activated account.
6. An invitation is mandatory. FE-001 creates a single-use opaque setup secret and persists `createdAt` and `expiresAt = createdAt + 48 hours` in the same invitation transaction, independent of SMTP delivery. Resend after the five-minute cooldown invalidates the prior version and creates a new 48-hour window at the new version's creation. Persist only the secret digest, key version, timestamps and use state. FE-007 receives a durable invitation reference and recipient, not the secret or full URL; at each send attempt an authorized FE-001 boundary materializes the same-version link transiently. FE-007 makes at most two definite SMTP attempts (initial plus one retry after about one minute). After two definite failures it records `FAILED`; the Account stays `PENDING_SETUP`. `UNKNOWN_OUTCOME` requires provider/operator reconciliation before any further send or rotation. The setup exchange accepts a current unexpired invitation whether automatic SMTP accepted it or the ADMIN delivered the mail outside the system. Mail copy states the exact expiry time, not a new 48-hour promise after delivery.

   **Re-materialization rule:** derive the opaque secret deterministically from invitation ID, version and a server-managed signing key (record the key version), then store a separate digest for comparison. This allows a retry or authorized manual-content retrieval to reproduce the same URL without storing the raw value. Key rotation must retain old versions until all corresponding invitations expire; if the key is unavailable, fail delivery closed and require explicit recovery rather than minting a different URL for the same version.

   **Manual delivery after failure:** Only when FE-007 has recorded two definite failed SMTP attempts and terminal `FAILED`, an authenticated ADMIN may open/copy the pinned subject, HTML and plain-text message with the current setup URL and exact expiry. FE-007 composes the response transiently through the FE-001 materialization facade with `Cache-Control: no-store`; no rendered secret-bearing content is persisted, logged or shown in general diagnostics. Opening/copying is audited without content or URL, does not rotate/extend the link or change `FAILED` to `SENT`, and does not prove outside delivery. If the link has expired, the button is disabled and the ADMIN must use the approved resend flow. Resend after a manual copy warns that it invalidates any copied/externally sent old link. `UNKNOWN_OUTCOME` does not unlock manual content until reconciled as definite failure.
7. The setup route validates the secret before issuing a short-lived Firebase custom token for the bound UID. The browser signs in to that UID and links either a new email/password credential or Google through the approved redirect flow. Provider email must match the intended normalized email; mismatch, linking conflict or interrupted redirect leaves PENDING_SETUP and triggers safe credential/session cleanup. Possession of the emailed one-time link proves mailbox control; backend rechecks the bound UID, intended email, setup completion and current active Location scope before atomically marking ACTIVE/consuming the invitation. Successful setup routes to the role home. Direct `/login` or `/register` for a reserved pending email is denied with neutral invitation guidance before Member bootstrap; no email-only claim or Member fallback is permitted. Expired/used links are denied and direct the user to ADMIN for resend.
8. ADMIN navigation contains Account management and permitted owner self-service only. Other internal routes enforce their explicit role allowlist before mounting or requesting data; backend business authorization remains authoritative. Remove the role-catalogue page, menu entry, API and standalone acceptance requirement. Keep only short role-selection guidance in create/edit forms.

## Contract and failure requirements

**Happy-case setup correction (2026-11-27):** FE-001 materializes the invitation URL from `app.frontend-base-url` (`FRONTEND_BASE_URL`, local default `http://localhost:5173`) and canonical browser route `/invitations/setup?secret=...`. The exchange endpoint is public and requires no bearer token; it returns `firebaseCustomToken`, `setupSession`, and `expiresAt` with `no-store`. If Firebase cannot issue a real custom token for the bound UID, exchange returns a provider-unavailable error and leaves the Account pending. The browser signs in with that token before authenticated profile/completion calls. Completion accepts `setupSession` and `method`; the backend verifies the bound UID and email plus method proof before consuming the invitation and returning `accountId`, `role`, `status`, and `homeRoute`. The route is `/staff/home` for STAFF and `/manager/dashboard` for MANAGER. For password, the browser updates the bound user's password, signs in with that email/password, and sends the resulting ID token so the backend can require Firebase `sign_in_provider=password`. For Google, the browser links via redirect on the bound user, resumes the setup session after return, and the backend checks the bound Firebase user has a `google.com` provider with the intended email. A failed or interrupted method leaves the Account `PENDING_SETUP`. Duplicate-email collision and account deletion are outside this correction.

- FE-001 owns identity, retirement, setup-secret state, activation, audit and recipient decision. FE-007 owns invitation template, queued delivery, attempt status and recovery. FE-001 persists an invitation outbox event in its Account transaction. FE-007 consumes it after commit and calls an FE-001 named materialization/status facade; the module dependency is `007 -> 001` only. The raw URL/secret is only in transient worker composition, the outgoing message or the ADMIN-only manual-content response after definite failure; it is never in notification persistence, general diagnostics, browser storage, audit or logs. The setup exchange returns an ephemeral Firebase custom token/setup session under `Cache-Control: no-store`.
- Create/review/export/retire/setup/resend endpoints require typed validation and error outcomes for missing/invalid email, collision role, stale review, already retired, provider unavailable, source unavailable, invalid/expired/used invitation, provider mismatch, inactive Location, cooldown and idempotency conflict. Do not disclose whether an arbitrary email exists to a non-ADMIN caller.
- Account and Firebase operations cannot share a transaction. Persist a resumable stage and correlation ID, use compensating deletion/revocation where safe, and never claim a stage completed from a timestamp alone. Retirement must coordinate old-identity revocation, de-identification and email reuse without an interval allowing either identity to inherit the other's role. A failed export or failed source query does not permit retirement.
- The JSON inventory is assembled by read-only facades owned by retail and workshop booking; the retail owner also returns the server-stored cart. Both owners return current nonterminal-obligation facts scoped to the old MEMBER Account ID. A definitive empty result from both is required before retirement; unknown/unavailable blocks. Each source returns its own snapshot and ownership IDs; FE-001 does not query another feature's repository or mutate retained business history. The review and export expose only data associated with the resolved MEMBER Account.

  **Consumer contract and temporary preview (2026-11-25):** FE-001 defines two read interfaces for the exact old Account ID: `RetailMemberReplacementReader` and `WorkshopMemberReplacementReader` in `accountmanagement.facade`. Their source-specific DTOs contain only the cart/order or booking fields used by ADMIN review/JSON and an obligation status `CLEAR`, `BLOCKED` or `UNAVAILABLE`. Local-only implementations in the `readyringsales/facade` and `workshopbooking/facade` packages return clearly marked `DEMO` records only for a configured demo Account ID, always with `UNAVAILABLE` and no trusted source version. The ADMIN may view/export these records as a sample, but cannot retire that MEMBER or create STAFF/MANAGER with the occupied email on this evidence. Other Account IDs and environments without real providers fail closed. No FE-003.1/FE-08 specification is changed in this round; their owners receive handoff notes for future live providers.

  **Retirement gate still open:** A live source provider must classify nonterminal obligations and return trustworthy versions; a fresh read alone cannot prevent a new accepted order/booking afterward. The three owners must agree on an acceptance/retirement fence before FE-001 enables MEMBER retirement and email release. Demo/`UNAVAILABLE` data never satisfies this gate. The fence must not cancel accepted work or discard late payment evidence.
