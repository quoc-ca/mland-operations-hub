## Decision Log

### D-01: Identity key and account ownership

**Decision**: Verified Firebase UID is the sole identity key. Login email is a current snapshot, not an ownership key.

**Rationale**: An email address can change, be shared across identity providers in edge cases, or be misrepresented by a browser/client. The UID is immutable and provider-verified. Using email as an ownership key would risk silent account merges on email collision.

**Alternatives considered**:
- Email as ownership key — rejected: unsafe merge risk, violates FR-001
- UUID generated by backend — rejected: unnecessary third identity; Firebase UID suffices when stored as an opaque server-side key

**Source**: FR-001; clarification session 2026-10-24

---

### D-02: Bootstrap behavior for unverified email

**Decision**: When an unknown Firebase UID has a valid (but unverified) email claim, bootstrap creates exactly one Account and one Profile. The Account carries the unverified email; the verification reminder is shown but sign-in is not blocked. Each protected function independently enforces its own verified-email requirement.

**Rationale**: Blocking registration at the verification step would prevent the user from receiving the verification email while signed in. Unverified email is an identity assurance state, not an account lifecycle state.

**Source**: FR-004; clarification 2026-10-26

---

### D-03: Bootstrap behavior for missing email claim

**Decision**: When an unknown Firebase UID has no valid email claim (e.g., certain social provider edge cases), no Account or Profile is created. The system gives safe alternative-method/recovery guidance without accepting a browser-supplied email as a substitute.

**Rationale**: Accepting client-supplied email would bypass the identity provider's email authority, violating FR-006 and Principle II.

**Alternatives considered**:
- Accept browser email — rejected: FR-006, Principle II
- Create Account without email — rejected: email is required for Profile full_name derivation and subsequent verification flows

**Source**: FR-034; clarification 2026-11-01

---

### D-04: Profile full_name default at bootstrap

**Decision**: Initial `full_name` is the portion before `@` of the current verified identity email. It is never a client-supplied value or the provider's display name.

**Rationale**: The email local part is a safe, user-recognizable default that comes from the identity provider without capturing PII beyond what the provider already supplies. Provider display names can contain unverified information.

**Source**: FR-007; clarification 2026-10-31

---

### D-05: PENDING_SETUP activation rule

**Decision**: A pending internal Account activates only when (a) the intended verified Firebase UID signs in, (b) the email is verified at the time of bootstrap, and (c) the assigned Workshop Location scope remains valid/active. Activation never creates or overwrites a Member Account.

**Rationale**: Premature activation could give internal access to an unverified or misidentified person. The three-condition gate ensures the intended person is controlling the identity before gaining internal capabilities.

**Source**: FR-013; clarification 2026-10-27

---

### D-06: Workshop scope in identity gate (actor resolution)

**Decision**: The identity gate (`IdentityGateFilter`) resolves a minimal current actor (`CurrentAccountActor`) containing only `accountId`, `role`, `status`, and `emailVerified`. It does NOT query Workshop Location scope. A location-scoped service obtains effective `activeWorkshopLocationIds` through the `findTargetFacts` or scope facade immediately before its authorization or mutation.

**Rationale**: Including Workshop scope in the identity gate would make every protected request dependent on Workshop Location availability. A Workshop Location outage would deny access to self-service Account operations that have no scope dependency, violating the isolation principle in FR-027.

**Alternatives considered**:
- Include `activeWorkshopLocationIds` in `CurrentAccountActor` — rejected: location outage blocks unrelated requests; adds complexity to the admission path
- Cache scope per session — rejected: V1 prohibits caching; stale scope could grant or deny access incorrectly

**Source**: FR-027; clarification 2026-10-27 / 2026-10-28; architecture.md approved decision table

### D-07: Internal facade typed contract (FR-028–FR-032)

**Decision**: FE-001 publishes exactly two methods at the Java module boundary for Workshop consumers:
1. `findTargetFacts(AccountId)` → `TargetFactsOutcome` (FOUND | NOT_FOUND | UNAVAILABLE)
2. `findEligibleRoster(workshopLocationId, requiredRole)` → `RosterOutcome` (AVAILABLE | UNAVAILABLE)

No REST endpoint, no generic Account directory, no cross-feature entity/DAO import.

**Rationale**: Named, typed methods with explicit outcome discriminants prevent the consumer from misinterpreting a temporary failure as a missing target (UNAVAILABLE ≠ NOT_FOUND). A REST endpoint would expose account data more broadly than the approved minimum.

**Alternatives considered**:
- Generic Account lookup REST endpoint — rejected: too broad; exposes more data than minimum; unauthorized callers could access
- Event-driven synchronization — rejected: V1 explicitly prohibits event-replicated Account facts; consumers must use current facts

**Source**: FR-028–FR-032; clarification 2026-10-27 / 2026-11-01; contracts/interfaces.md

---

### D-08: Consumer behavior on UNAVAILABLE

**Decision**: When `findTargetFacts` or the scope query returns `UNAVAILABLE`, the dependent mutation must not start or commit. The consumer returns `503`, preserves safe unsaved user input, and performs no background retry, cache lookup, or fallback scope resolution.

**Rationale**: Starting a mutation with unverified scope could grant or deny capabilities based on stale data. The fail-closed rule ensures correctness at the cost of a user-visible retry, which is acceptable for the targeted use case.

**Source**: FR-031; clarification 2026-10-28

---

### D-09: TARGET_NOT_ELIGIBLE mapping

**Decision**: `NOT_FOUND` and any `FOUND` result where the consumer's own approved role/status/scope rule is not met are mapped to the generic `409 TARGET_NOT_ELIGIBLE`. No lifecycle detail is exposed. `UNAVAILABLE` maps to `503`.

**Rationale**: Distinguishing "target not found" from "target found but wrong role" would expose account lifecycle information to the Workshop actor. Generic ineligibility prevents information leakage while giving the consumer an actionable signal.

**Source**: FR-030; clarification 2026-10-27

---

### D-10: Audit outcome schema — approved baseline

**Decision**: `AccountAuditEvent.outcome` column: Java `AuditOutcome` enum with exactly `SUCCESS` and `FAILURE`, persisted as `VARCHAR(16)`. An append-only Flyway migration changes the existing `outcome` column from MySQL `ENUM('SUCCESS','FAILURE')` to `VARCHAR(16) NOT NULL`. No edit to the applied `V5__account_management.sql`.

**Rationale**: Hibernate schema validation (`ddl-auto=validate`) rejects a `VARCHAR`-mapped field against a MySQL `ENUM` column, preventing `EntityManagerFactory` startup. `VARCHAR(16)` is compatible with both Hibernate validation and the enum values without requiring a MySQL `ENUM`, which is harder to extend safely.

**Alternatives considered**:
- Map Java field as `@Enumerated(EnumType.STRING)` to MySQL ENUM — rejected: ENUM type limits future values without another DDL migration; also causes Hibernate validation failure on current mapping
- Use free `String` in Java — rejected: callers could persist arbitrary values; approved contract requires exactly two values

**Approved by**: Tech Lead Phan Sơn, 2026-10-28
**Source**: data-model.md §Audit outcome storage contract; clarification 2026-10-28

### D-11: Idempotency for internal account creation

**Decision**: Each creation request carries a client-supplied idempotency key. The backend stores a normalized digest of the request alongside the key. Same key + same digest → return preserved result (no second account). Same key + different digest → `409` (changed request rejected; no second account). A new key + any digest → new request.

**Rationale**: Internal account creation involves external Firebase calls that cannot be rolled back cleanly. Idempotency enables safe client retry after a lost response without risk of duplicate accounts or duplicate invitations.

**Source**: FR-014; clarification 2026-10-25

---

### D-12: CORS and credential transport (local)

**Decision**: V1 local policy:
- `Authorization: Bearer {Firebase ID token}` — sole credential transport
- Allowed CORS origin: exactly `http://localhost:5173`
- `Access-Control-Allow-Credentials: false`
- No browser auth cookie, server session, application JWT, or refresh-token system
- `SecurityConfiguration` sets an explicit public-route allowlist; all other routes deny by default

**Rationale**: Bearer-only transport eliminates CSRF risk for the approved credential flow and avoids the complexity of a separate session store or refresh-token system. Exact-origin CORS prevents wildcard exposure. A future cookie-based flow requires a new approved CORS/CSRF/session/logout design.

**Approved by**: Tech Lead Phan Sơn, 2026-10-28
**Source**: architecture.md approved decisions; clarification 2026-10-28

### D-13: Flyway version convention

**Decision**: Repository-wide, append-only, increasing integer sequence. An owner checks and reserves the highest current number before creating a new migration file. Applied or merged migrations must not have their version number changed.

**Rationale**: A shared sequence prevents version conflicts across feature branches. Reserving the next number before branching avoids two teams using the same version in concurrent branches.

**Source**: clarification 2026-10-26

---

### D-14: Error ownership and envelope

**Decision**:
- Identity gate owns admission `401` and `403`
- FE-001 owns its validation and business errors
- Shared technical fallback owns only unhandled technical failures
- Error envelope: `{ code, message, correlationId, timestamp, fieldErrors? }`
- No stack trace, raw token, Firebase UID, or unauthorized target detail in any response

**Approved by**: Tech Lead Phan Sơn, 2026-10-28
**Source**: architecture.md; design/workflows.md WF-06; clarification 2026-10-28

### D-15: Audit persistence failure behavior

**Decision**: An audit persistence failure must not roll back, block, or replace the original business outcome. The system emits a non-sensitive operational signal keyed by the correlation ID instead of claiming the audit was stored. Only successfully retained audit evidence counts toward the 5-year retention requirement.

**Rationale**: Making the audit path a hard transactional dependency would tie business outcomes to audit infrastructure availability. The approved model: best-effort audit with safe operational signaling.

**Source**: FR-023; clarification 2026-10-29

---

### D-16: Workshop target display name

**Decision**: Display name in the roster is the current `Account Profile.full_name`. No separate personnel field is created. UI may show the opaque `accountId` alongside the display name to distinguish duplicate names.

**Source**: FR-029; clarification 2026-10-28

---

### D-17: Account ID representation

**Decision**: REST/UI: opaque string containing a canonical positive integer (e.g., `"42"`). Malformed, padded (`"042"`), signed (`"-1"`), blank, provider UID, or alternate identifier representations are invalid. Java facade: uses a `AccountId` boundary type wrapping the same value — no Personnel ID or UUID.

**Source**: FR-033; clarification 2026-10-28

---

### D-18: Scope delivery to Workshop (FR-027 vs FR-028)

**Decision**: `CurrentAccountActor` (identity gate output) does not include Workshop scope. `TargetAccountFacts.FOUND` includes `activeWorkshopLocationIds` = active Account assignments ∩ currently active authoritative Workshop Locations. This effective scope is resolved per-action, never cached, never event-replicated in V1.

**Source**: FR-027–FR-028; clarification 2026-10-27 / 2026-10-28; architecture.md approved decisions
